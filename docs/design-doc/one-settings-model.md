# One settings model, unchanged product behavior

This is a replacement of the organization and personal settings implementation, not a redesign of the settings product. The comparison point is `main` before the cutover, not an intermediate draft of this PR.

## Contract and acceptance criteria

1. **One model and one organization document.** Define configurable organization preferences once as a Pydantic model. Store the organization's settings in one JSON object. The row identifies the owner. Keep an explicit inventory of fields, legacy columns, callers, and replacement paths. Identities, memberships, payment transactions and credential vault records are not themselves preferences; settings referencing a separately managed resource must not duplicate its secrets.
2. **Inheritance by default.** Resolve schema defaults, organization contribution, then personal contribution. An empty personal contribution follows the organization on every read. An unchanged save preserves ownership, including migrated equal-value pins. Reset removes only the local contribution. Absence, null and empty collections are distinct.
3. **One typed editor.** Existing UI controls translate their intent into generic model operations: change value, extend list, delete from list, or inherit. Persist enough intent to replay relative list edits against later parent values. For example, adding C to inherited [A,B] must still include D after the parent adds D. Validate the composed model, not an incomplete row. Never derive ownership by subtracting two resolved snapshots. Let the SDK handle typed reconciliation, variants and secret serialization; prove the editor on an unrelated Pydantic model.
4. **Organization-admin policy.** Represent editable paths and allowed operations as data. Enterprise checks tenant, membership, actor and organization policy server-side in the same transaction as the write. Ancestor replacement, batch operations and reset must not bypass a denial on a descendant. The UI consumes the same policy. Initialize it from existing access rules so a cutover neither expands nor revokes access.
5. **Remove the replaced implementations.** For every migrated field, identify the old writer, storage, special-purpose editor and permissions code that disappear. Keep API adapters only where compatibility requires them; adapters translate, not reimplement. No permanent dual writes. Audit background jobs, management commands, launch paths and the standalone store as well as HTTP handlers. Report production and whole-PR line counts against main.
6. **Within the scope of this PR, user-facing behavior does not change.** Existing controls, names, navigation, HTTP contracts, allowed actions, default values and launches remain compatible. Use the generic engine behind existing controls. A new permission screen, team scope, profile workflow or independent member LLM selection is not part of this change. Differences in implementation are not grounds for approving a different product result.

## Release proof

Before cutover, inventory the settings surfaces and exercise the existing product as admins, ordinary members and unauthorized callers. Replay the same requests after migration and compare responses, effective settings, authorization and launches. Cover list edits followed by parent changes, duplicate list values, variant switches, concurrent edits, secret redaction and wrong-key failures. Reject stale revisions before comparing values. Reads must not write.

Rehearse on disposable PostgreSQL with representative historical data. Stop rather than guess when a legacy value cannot be converted without changing behavior. Verify inherited values and explicit pins after changing the parent, not merely immediately after migration. Preserve encrypted resources and avoid logging their contents. A cutover that removes columns requires draining incompatible old writers and a restore-tested backup. No deployment is authorized by this design.

A six-out-of-six review requires evidence for each numbered item, passing checks on the current PR head, and no unresolved merge conflicts or blocking review findings. A document or an isolated helper test does not prove integration.
