# Organization, team and personal settings: upgrade notes

Organization settings supply the default. Team execution limits apply only in the explicitly selected team; personal overrides apply last. For example, submitting 80 while inheriting an organization limit of 80 does not create a personal override. Changing a personal override to the parent's current value removes it. Existing pins survive an unchanged submit. Existing users do not have to create a team or choose a profile.

The initial team API permits only `conversation_settings.max_iterations` and `agent_settings.tool_concurrency_limit`. Editing requires team membership in the current organization and permission to edit organization settings. After a revision conflict, reload before saving. This change does not make credentials or other catalogs team-editable.

## Client cutover

Upgrade API clients and reload open browser tabs in the maintenance window. Personal and organization clients submit ordinary values, for example `{"conversation_settings":{"max_iterations":80}}` or `{"agent_settings":{"tool_concurrency_limit":3}}`. The settings write endpoints no longer accept `operations`, `agent_settings_diff`, or `conversation_settings_diff`. Omitted fields are unchanged. Team edits wrap the same fields in `settings` and echo both `revision` and `parent_updated_at` from the team GET.

## Operator cutover

**Do not do a normal rolling upgrade across this schema change.** Old application processes cannot read the new schema. There is no feature flag that restores removed columns. Use candidate tooling against a clean copy first. Use the released chart/image digests, not mutable tags. The numbers below apply to the candidate based on main revision 224 (Bitbucket DC login provider); verify ancestry if main moves. Never stamp over a conflicting revision from an experimental installation.

1. Before announcing an outage, record the deployed chart, images, DB revision, rollback artifacts, and which controllers can start writers. Include API pods, workers, cron jobs, autoscalers, and GitOps reconciliation. Measure backup/restore and upgrade on representative data. Agree on the maximum interruption, rollback deadline and decision-maker.
2. In the **candidate image** using the pre-upgrade database connection, run `python -m migrations.versions.226_consolidate_settings_documents`. This checks the legacy schema in a read-only transaction. Nonzero means stop. The same converter runs during preflight and upgrade. It reports counts, not row contents. It stops on unknown or invalid fields, ambiguous legacy map updates, or meaningful inline credentials; deleting or masking an unrecognized value is not a repair. Move inline credentials through the organization's approved encrypted credential migration process before trying again. Existing encrypted credential columns and resource references are not rewritten; keep the deployed keyring, including previous keys. Never send credential-bearing rows or backups in support tickets. A successful check is not permission to migrate while old writers are active.
3. Block new requests/launches; drain and stop old readers and writers and prevent controllers from recreating them. Check active conversations and external workers explicitly. Do not proceed if quiescence cannot be established. Take and verify a restorable backup under the operator's normal access controls. Record point-in-time recovery position if applicable.
4. Run `alembic upgrade head` once from the candidate image with those database settings. Check `alembic current` against the candidate head (227 here). Start only the new version, keeping general traffic blocked. On the restored rehearsal copy, compare the legacy and migrated effective settings and inspect local ownership. Exercise OpenHands and ACP, a legacy tool-switch row, an inheriting member and a member pinned to the same value. Change the organization defaults and variant, then verify that the inheritor follows and the pins stay. Verify old-key LLM and MCP reads without exporting secrets. In the maintenance window, also smoke-test inheritance after reset, a forbidden team, and an actual conversation. Retain aggregate results, not settings documents. Reopen traffic and resume scheduled work only after sign-off.
5. **Recovery before reopening:** stop candidate processes, restore the verified pre-window backup, deploy the matching old images, then verify old settings reads and writes before reopening. Do not merely roll Helm back against the new schema. Downgrade 226 restores the column layout, not the original values and encodings; use the backup for rollback. Do not stamp a database already upgraded by a different revision-226 implementation. **After reopening:** freeze writes again and evaluate forward repair first. Downgrading 227 deletes teams and memberships, downgrading 225 drops personal LLM selection, and restoring a snapshot loses all intervening writes, not just settings. Require an explicit recovery decision and reconciliation plan.
