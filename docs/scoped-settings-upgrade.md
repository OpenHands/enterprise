# Organization, team and personal settings: upgrade notes

Organization settings supply the default. Team execution limits apply only in the explicitly selected team; personal overrides apply last. For example, submitting 80 while inheriting an organization limit of 80 does not create a personal override. Changing a personal override to the parent's current value removes it. Existing pins survive an unchanged submit. Existing users do not have to create a team or choose a profile.

The initial team API permits only `conversation_settings.max_iterations` and `agent_settings.tool_concurrency_limit`. Editing requires team membership in the current organization and permission to edit organization settings. After a revision conflict, reload before saving. This change does not make credentials or other catalogs team-editable.

## Client cutover

Upgrade API clients and reload open browser tabs in the maintenance window. Personal and organization clients submit ordinary values, for example `{"conversation_settings":{"max_iterations":80}}` or `{"agent_settings":{"tool_concurrency_limit":3}}`. Neither `operations` nor `conversation_settings_diff` is accepted. Omitted fields are unchanged. Team edits wrap the same fields in `settings` and require the current team revision. Other agent preferences still use `agent_settings_diff`.

## Operator cutover

**Do not do a normal rolling upgrade across this schema change.** Old application processes cannot read the new schema. There is no feature flag that restores removed columns. Use candidate tooling against a clean copy first. Use the released chart/image digests, not mutable tags. The numbers below apply to the candidate based on main revision 221 (worklogs); verify ancestry if main moves. Never stamp over a conflicting revision from an experimental installation.

1. Before announcing an outage, record the deployed chart, images, DB revision, rollback artifacts, and which controllers can start writers. Include API pods, workers, cron jobs, autoscalers, and GitOps reconciliation. Measure backup/restore and upgrade on representative data. Agree on the maximum interruption, rollback deadline and decision-maker.
2. In the **candidate image** using the pre-upgrade database connection, run `python -m migrations.versions.223_consolidate_settings_documents`. This checks the legacy schema in a read-only transaction. Nonzero means stop. The credential check reports counts, not row contents. Move any real inline credentials through the organization's approved encrypted credential migration process before trying again. Never send credential-bearing rows or backups in support tickets. A successful check is not permission to migrate while old writers are active.
3. Block new requests/launches; drain and stop old readers and writers and prevent controllers from recreating them. Check active conversations and external workers explicitly. Do not proceed if quiescence cannot be established. Take and verify a restorable backup under the operator's normal access controls. Record point-in-time recovery position if applicable.
4. Run `alembic upgrade head` once from the candidate image with those database settings. Check `alembic current` against the candidate head (224 here). Start only the new version, keeping general traffic blocked. Smoke-test a member without overrides, a pinned member, inheritance after reset, a forbidden team, and an actual conversation. Retain aggregate results, not settings documents. Reopen traffic and resume scheduled work only after sign-off.
5. **Recovery before reopening:** stop candidate processes, restore the verified pre-window backup or use the exact downgrade path already rehearsed for the source revision, deploy the matching old images, then verify old settings reads and writes before reopening. Do not merely roll Helm back against the new schema. **After reopening:** freeze writes again and evaluate forward repair first. Downgrading 224 deletes teams and memberships, downgrading 222 drops personal LLM selection, and restoring a snapshot loses all intervening writes, not just settings. Require an explicit recovery decision and reconciliation plan.
